1. Why polling instead of event-driven?

What the code suggests. The worker has a lease, a heartbeat thread, an execution_fence and retry backoff stored in the DB (next_retry_at). Those mechanisms make the job row the source of truth, and polling is the simplest way to read it. Polling gives you:

No extra infrastructure. The system already runs Postgres, Milvus and Supabase. A broker (Redis, RabbitMQ, SQS, Kafka) would be one more thing to deploy and monitor.
Crash recovery for free. If a worker dies, its lease expires and another worker's next poll claims the job. A broker needs a visibility timeout or ack/redelivery for the same effect.
No lost-message problem. A message can be lost between "row committed" and "message published". Polling has nothing to lose, because the row is the work.

What it costs. There is up to poll_seconds of latency before a job starts, plus an idle query on every poll. I didn't read poll_seconds, so I don't know the value. For document ingestion, where parsing and embedding take seconds to minutes, a 1–5 second delay is irrelevant.

Event-driven wouldn't remove the hard parts. With a broker you would still need the lease, fencing and idempotent publication, because brokers deliver at least once and consumers can die mid-job. So most of the complexity in worker.py would stay.

The usual middle ground is to keep the DB as the truth and add a wake-up hint, such as Postgres LISTEN/NOTIFY or a Redis ping after submit(). The worker still polls as a fallback, but reacts instantly when notified. If the delay ever matters, this is a small change.

Event-driven becomes worth it when you have many workers hammering the DB, need sub-second start times, or have multi-stage pipelines (parse, embed and index as separate services).

2. Is using the DB to link upload and indexing best practice?

For this scale, yes. It is a recognized pattern: a DB-backed job queue, close to the transactional outbox pattern. Postgres-based queues are used in production by many teams.

Why it fits here:

Atomicity. submit() calls catalog.reserve_upload(...), which creates the document version and the job together. A broker would force you to write to the DB and publish a message separately, and either could fail.
Free progress UI. The "快速入库" step bars come from index_job_view(), which just reads the job row (current_step, step_state, processed_chunks). With a broker you'd still need a state store for this.
Safe retries and operations. Attempts, error codes and dead_letter status are queryable rows. The list-cleanup and requeue-cleanup commands in indexing.py are an operator tool built on that.
The blob stays out of the DB. The job carries only a source_object_key. The file lives in Supabase storage (push_local on upload, ensure_local in the worker). That is the right split: metadata and state in the DB, bytes in object storage.

Caveats:

I didn't read catalog.claim_index_job (catalog.py is about 149 KB). Safe multi-worker claiming normally needs an atomic claim, such as SELECT ... FOR UPDATE SKIP LOCKED or a conditional UPDATE ... WHERE with a lease check. Check that it does, or two workers may claim the same job.
Progress writes hit the DB often (per 50-chunk vector batch, plus heartbeats). That is fine for one worker, but it adds up under load.
Polling queries and finished job rows grow over time, so you need an index on the claim columns and a retention policy.
Throughput tops out far below a real broker. That doesn't matter for document upload volumes.

Verdict: keep the DB as the coordination layer. Optionally add a NOTIFY hint for instant pickup. Move to a broker only if you hit real limits, such as many concurrent workers or independently scaled pipeline stages.
